From command to report

This lesson answers your question: exactly what happens after you run the command?

The short answer

CLI command
  -> load languages.toml
  -> load optional pre-llm.toml
  -> scan folders and discover projects
  -> detect commands for each project
  -> run Build, Lint, Tests, Coverage
  -> apply gates and interpret results
  -> write terminal table, logs, and JSON report
Correction to the common mental model: the script does not first scan every source-file extension and then run every language it recognizes. A project is primarily discovered by a recognized build file. Extensions are used afterward for ownership and warnings.

1. The command starts the entry point

For example:

py -3 pre_llm_checks.py --path C:\code\my-repo --dry-run

The entry point validates arguments and the path, loads the language rulebook, reads optional configuration, and prints the trust notice before project commands run.

2. languages.toml is the rulebook

The script loads languages.toml. Each language entry describes:

  • Source extensions.
  • Build-file patterns that mark a project.
  • Priority when multiple build files exist.
  • Stage names and script mappings.
  • Built-in commands.
  • Configuration files and plugins.
  • Dependency error patterns.
  • No-test patterns.
  • Coverage report files.
  • Whether the language is tested.

It is data-driven: the discovery and detection code reads these rules instead of hard-coding every language in Python.

3. The optional pre-llm.toml is loaded

If present at the repository root, it adds ignored paths and can replace detected commands for a project:

ignore = ["legacy"]

[[project]]
path = "backend"
lint = "npm run check-style"
tests = "pytest -q"

A valid override counts as project-defined. A malformed configuration produces a tool error rather than a Python crash.

4. Discovery scans folders

The scanner walks the folder tree while skipping directories such as .git, node_modules, target, build, dist, vendor, __pycache__, and .pre-llm.

At each folder it compares filenames against the build_files patterns from the rulebook. Examples:

  • package.json creates a JavaScript/TypeScript project.
  • pyproject.toml or requirements.txt creates a Python project.
  • pom.xml creates a Maven Java project.
  • go.mod creates a Go project.
  • *.sln or *.csproj creates a .NET project.

The result is one project per folder per language. If the same folder has two build files for one language, priority chooses the primary file while both are retained as metadata.

5. What happens to extensions?

Your understanding is partly correct:

  • Supported extension + no owning project: the tool can report no_project because source exists without its language's build file.
  • Known unsupported extension: the tool can report unsupported_extension, for example Scala or Dart when no rulebook entry exists.
  • Unknown extension: it is generally not a project and is not necessarily reported.
  • Build file present: the build file creates the project; the project then owns files according to the nearest-build-file and language rules.
Key distinction: extensions describe source ownership and warnings. Build files are the primary project markers. A lone .py file does not automatically make a Python project.

6. Detection chooses commands

For each discovered project, detection checks only project-defined sources:

  1. Scripts in the build file.
  2. Recognized config files.
  3. Plugins in Maven/Gradle files.
  4. Language built-ins declared by the rulebook.
  5. Per-project overrides.

A package merely listed in devDependencies is not enough. For a script, names are matched exactly or by prefix: lint and lint:types both map to Lint.

Risky commands such as lint:fix, dev, deploy, commands containing --fix, or commands containing --write are skipped and recorded. Exact duplicate commands run once.

7. Execution is staged

For each project the orchestrator runs:

  1. Build - compilation or project-defined build.
  2. Lint - project-selected static checks.
  3. Tests - project-selected tests.
  4. Coverage - tests or coverage command plus report reading.

Python commonly has Build SKIP because it has no build command. That does not block Lint, Tests, or Coverage.

Gates

  • Build FAIL/TIMEOUT -> later stages SKIP. --lint-anyway still permits Lint.
  • Lint FAIL/TIMEOUT -> Tests and Coverage SKIP.
  • Tests FAIL/TIMEOUT -> Coverage SKIP.
  • No tests found -> Tests SKIP and Coverage FAIL.

8. The runner executes safely

Commands are converted to argument lists and run with shell=False. It prefers wrappers such as mvnw and gradlew, enforces per-stage timeouts, kills the whole process tree on timeout or Ctrl+C, and decodes unusual output bytes safely.

In a dry run, this execution step is replaced by display-only planning.

9. The result is written

The terminal table shows the worst stage result for each project. Full logs go under .pre-llm/logs/. The JSON report records project metadata, commands, sources, statuses, durations, masked output tails, log paths, warnings, counts, and environment information.
