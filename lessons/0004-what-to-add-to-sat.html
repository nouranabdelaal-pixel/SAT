What should SAT add?

Today SAT is an evidence collector. Other tools add semantic review, PR automation, dependency security, vulnerability intelligence, license checks, and structured finding formats.

Keep the core boundary

Core: local, deterministic, read-only, project-defined commands, dry-run, safe runner, terminal table, JSON evidence.

Best next additions

  1. Structured parsers: read SARIF and JUnit XML into the existing findings field.
  2. Security adapters: explicitly run tools such as dependency or SAST scanners only when configured by the project.
  3. Better secret masking: cover JSON secrets, space-separated flags, and common token formats.
  4. CI formats: output GitHub Checks, SARIF, or JUnit without changing the core evidence model.
  5. Optional policies: coverage minimums and strict no-test mode, only after a specification change.

Do not hide risky behavior

Dependency installation, network access, hosted AI review, and repository mutation should be opt-in, isolated, logged, and visible in the report. Never silently add them to the default run.

Retrieval practice

Explain in your own words: Why is Black Duck complementary to SAT rather than a replacement? Why should SARIF parsing be easier to add than AI review? What should happen if a security adapter is not installed?

Check your answer

Black Duck analyzes dependency/security/license risk while SAT verifies the repository's own checks. SARIF parsing consumes standardized evidence, while AI review introduces a new semantic/service layer. A missing adapter should produce a transparent warning, not a fake pass.
