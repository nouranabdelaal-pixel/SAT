Pre-LLM Checks

A complete standalone study guide for using, understanding, testing, and extending the SAT project: Pre-LLM Checks.

Central idea: Pre-LLM Checks gathers evidence before an AI reviews a repository. It asks whether the repository builds, lints, tests, and reports coverage. It does not use AI, fix code, install packages, or decide whether code is good.

1. Learning outcomes

After studying this guide, you should be able to:

  • Run a safe preview and a real check on a repository.
  • Explain how projects are discovered and how commands are selected.
  • Interpret every important stage status and exit code.
  • Read pre-llm-report.json as evidence for an AI reviewer.
  • Diagnose gates, missing tools, missing dependencies, stale coverage, and no-test cases.
  • Explain the architecture and data-driven language system.
  • Identify current v1 limitations and known implementation gaps.
  • Extend the rulebook and fixtures without weakening safety.

2. What the tool does

One invocation scans a folder, finds supported projects, determines which commands each project has defined, runs the commands in a controlled order, and produces two outputs:

  • A human-readable terminal table.
  • A machine-readable pre-llm-report.json file for an AI reviewer.

The tool needs Python 3.11 or newer and no third-party packages. The tool itself does not install anything.

Evidence, not judgement: a coverage result of 42% is reported, but v1 does not decide that 42% is unacceptable. A missing linter is reported as a warning, not silently treated as a pass.

3. Safety model

The tool is designed to be read-only with respect to the project source. However, the commands it runs belong to the project and can contain arbitrary behavior.

Rules

  • It does not change source code.
  • It does not install dependencies.
  • It does not run ordinary fixers or formatters.
  • It runs commands as argument lists with shell=False.
  • It runs from each project's own folder.
  • It masks many secrets in commands, output, logs, and reports.
  • It writes logs and the report; with --add-gitignore, it may also update .gitignore.
  • It has no sandbox in v1.

Every real run starts with a trust notice. On unfamiliar code, preview first:

py -3 pre_llm_checks.py --path C:\code\unknown-repo --dry-run

Review every planned command before removing --dry-run.

4. Installation and first run

There is no package installation for the tool. Place the SAT project somewhere accessible and use Python 3.11+.

Windows PowerShell

py -3 C:\tools\SAT\pre_llm_checks.py --path C:\code\my-repo --dry-run
py -3 C:\tools\SAT\pre_llm_checks.py --path C:\code\my-repo

macOS or Linux

python3 /path/to/SAT/pre_llm_checks.py --path ~/code/my-repo --dry-run
python3 /path/to/SAT/pre_llm_checks.py --path ~/code/my-repo

Without --path, the current folder is checked. The default report is written to the current folder as pre-llm-report.json; use --output to choose another location.

6. The pipeline

The normal flow is:

Find projects
    -> Detect project-defined commands
    -> Build
    -> Lint
    -> Tests
    -> Coverage
    -> Terminal table + JSON report

Each project is independent. A failing project does not stop other projects from running.

Build gate

If Build fails or times out, Lint, Tests, and Coverage are skipped for that project. --lint-anyway makes an exception for Lint. Build WARN or SKIP does not activate the gate.

Lint gate

If Lint fails or times out, Tests and Coverage are skipped. A linter warning, missing linter, or skipped lint stage does not activate the gate.

Tests gate

If Tests fails or times out, Coverage is skipped. If no tests are found, Tests becomes SKIP and Coverage becomes FAIL with reason no_tests_found. This prevents an empty test suite from appearing healthy.

Coverage behavior

Coverage often runs tests again with coverage enabled. It reads fresh reports written during that coverage run. Old reports are ignored. If no report file exists, it may parse a percentage from command output. There is no minimum coverage threshold in v1.

8. Project discovery

A project is a folder containing a recognized build file. The rulebook in languages.toml identifies build files and languages.

Recognized project markers

  • Python: pyproject.toml, requirements.txt
  • Java/Kotlin: pom.xml, build.gradle, build.gradle.kts
  • JavaScript/TypeScript: package.json
  • Go: go.mod
  • C#/.NET: .sln, .slnx, .csproj
  • Rust: Cargo.toml
  • PHP: composer.json
  • Ruby: Gemfile
  • Swift: Package.swift
  • C/C++: CMakeLists.txt, Makefile, meson.build

Discovery rules

  • The nearest build file owns source files.
  • One project is created per folder per language.
  • For Python, pyproject.toml has priority over requirements.txt, but both may be listed.
  • For .NET, a solution has priority over a project file.
  • Maven modules and Gradle subprojects are folded into their root build where the rulebook says the root owns them.
  • Skip directories include dependency, build, generated, cache, and tool folders such as node_modules, .git, target, dist, vendor, bin, obj, __pycache__, .pre-llm, and others.
  • Source files without a build file produce warnings rather than becoming projects.

9. How commands are selected

A command is eligible only when the project itself defines or selects it. The tool does not run every installed tool it can find.

  1. Build-file scripts: for example, lint, lint:types, test, or build in package.json.
  2. Configuration files: for example .golangci.yml, .rubocop.yml, pytest.ini, or tsconfig.json.
  3. Build plugins: for example Checkstyle or JaCoCo in Maven/Gradle configuration.
  4. Language built-ins: for example go test ./..., cargo build, or dotnet build where the language rules define them.
  5. Overrides: commands in pre-llm.toml replace detected commands for a selected project and stage.

Exact names and prefixes match stage names. For example, lint and lint:types map to Lint. Identical commands run once; different arguments are different commands.

Scripts intentionally skipped

Scripts are skipped when their names end in :fix, :watch, :dev, :serve, :e2e, :docker, or :deploy, or when their command uses --fix or --write. They appear under skipped_scripts with a reason.

Important v1 gap: a pre-llm.toml override is trusted as project-defined. If an owner writes a fixer such as ruff check --fix . there, the override may run it. This is a known safety gap.

10. Configure overrides with pre-llm.toml

Place an optional pre-llm.toml at the repository root:

ignore = ["legacy", "generated"]

[[project]]
path = "backend"
lint = "npm run check-style"
tests = "pytest -q"

ignore adds paths to the discovery skip list. A project override counts as project-defined and replaces automatic detection for that stage. v1 supports only ignore paths and per-project stage overrides.

12. Runner behavior

  • Commands use argument lists, not shell strings.
  • Executable lookup handles platform endings such as .cmd and .exe.
  • Maven and Gradle wrappers win over global commands.
  • Default limits are Build 10 minutes, Lint 5 minutes, Tests 15 minutes, Coverage 15 minutes.
  • A timeout kills the whole child process tree, not only the parent process.
  • Ctrl+C kills the running tree, marks the run interrupted, writes the report, and exits 130.
  • Output is decoded with UTF-8 replacement so unusual bytes do not crash the run.
  • Full output goes to logs; the report keeps a bounded tail.

13. Coverage behavior

The tool does not calculate coverage itself. It runs the project's coverage command and reads supported output formats.

  • JaCoCo XML for Java/Kotlin.
  • Cobertura XML for Python, .NET, Rust, and related tools.
  • Istanbul JSON summary or lcov for JavaScript/TypeScript.
  • Go cover profiles.
  • SimpleCov JSON for Ruby.
  • llvm-cov JSON for Swift.

Coverage files must be fresh: a file older than the start of the Coverage stage is ignored. If multiple reports exist, results are not averaged; the lowest line percentage is shown. A broken report is ignored with a warning. v1 has no threshold and does not parse structured findings from coverage or test formats.

14. The JSON report

The report is intended for an AI reviewer. It is always written for a real run, including after early errors or interruption. A normal report contains:

{
  "schema_version": "1.0",
  "summary": {
    "status": "pass",
    "project_count": 1,
    "counts": {"pass": 4, "fail": 0, "timeout": 0,
               "warning": 0, "skipped": 0, "interrupted": 0},
    "generated_at": "UTC ISO-8601 timestamp"
  },
  "warnings": [],
  "projects": [],
  "environment": {"os": "...", "runners": {}}
}

Important fields

FieldMeaning
schema_versionVersion of the report shape. Shape changes must bump it.
summary.statusOverall pass, fail, interrupted, error, or no_project state.
summary.countsCounts table cells by status across projects and stages.
projectsProject path, language, build files, skipped scripts, commands, and warnings.
commandsStage, argument list, source, status, duration, output tail, log path, reason, and reserved findings.
environmentOperating system and versions of tools that actually ran.
findingsnull in v1; structured JUnit/SARIF parsing is not implemented.
truncatedPresent only when the report exceeded its approximate size budget.

Output tails default to 50 lines, each limited to 500 characters. The total report is capped around 200 KB so it remains usable in an AI context window. Paths are relative to the repository root and use forward slashes.

16. Known gaps and not-yet-handled behavior

Confirmed implementation gaps

  1. Incomplete secret masking: JSON-style secrets such as "password": "value", space-separated flags such as --password value, and some bare GitHub/AWS keys may remain visible.
  2. Unsafe overrides: a trusted override can explicitly contain a fixer command.
  3. Symlinked folders: discovery does not follow symlinked folders, and this can be silent.
  4. Python version message: Python 3.10 may crash before the tool can provide a friendly version error or report.
  5. Early scan interruption: Ctrl+C during a very large folder scan is not handled as cleanly as Ctrl+C during command execution.
  6. Untested languages: Rust, PHP, Swift, and C/C++ are not fully validated with real tools in the project record.

Features intentionally outside v1

  • Parallel project execution
  • Language filtering
  • Changed-files-only checks
  • Coverage thresholds
  • Dependency installation
  • CI or remote integration
  • Sandboxing
  • Zip input
  • Git URL input
  • Single-file input
  • Tool-specific finding parsers
  • JUnit XML and SARIF readers

Low coverage does not fail a run in v1. No tests do cause Coverage to fail. Optional strict mode and a minimum coverage flag were proposed but require a specification change.

17. Architecture

The project is divided into focused Python modules:

ModuleResponsibility
pre_llm_checks.pyEntry point, CLI parsing, path validation, trust notice, report coordination.
discovery.pyWalks the repository and finds projects.
detection.pyFinds commands, skips risky scripts, removes duplicates, loads overrides.
runner.pyExecutes one command with no shell, timeouts, process-tree cleanup, and decoding.
orchestrator.pyRuns stages in order and applies gates/status rules.
coverage_readers.pyReads supported coverage files and checks freshness.
output.pyRenders the terminal table, environment data, and exit logic.
masking.pyRemoves recognized secrets from output.
languages.tomlData-driven language rulebook: files, commands, patterns, coverage, and tested state.

The design principle is: language knowledge belongs in data, not Python control flow. Adding a language should normally mean adding a rulebook entry and fixtures rather than changing the engine.

18. How to test the project

The automated suite uses pytest:

py -3 -m pytest -q

The project uses black-box expectations around exit codes, terminal output, and report structure. Fake-tool tests replace real command execution so language planning can be tested without every compiler installed. Golden files preserve expected output. Manual scripts run real tools against sample projects.

Fixture categories

  • Working project.
  • Build failure.
  • Test failure.
  • Lint failure.
  • No tests.
  • No linter.
  • Risky scripts.
  • Duplicate scripts.
  • Hanging command.
  • Monorepo.
  • Missing dependencies.
  • Interrupted run.

When intentionally changing report shape, update the schema version and regenerate/review golden files. Never silently update golden output without understanding the behavior change.

19. Extending the tool with a language

  1. Add a [language.name] entry to languages.toml.
  2. Define extensions, build files, stage names, built-in commands, configuration commands, dependency checks, no-test patterns, and coverage files.
  3. Add fixtures for applicable successful and failing cases.
  4. Record expected results.
  5. Add the successful fixture to fake-run coverage and generate its golden file deliberately.
  6. Run the full test suite and review output.
  7. Mark tested = true only after every applicable fixture passes.
Design check: a new language should not bypass the safety rules. It must not install tools, run fixers, or infer commands merely because a package happens to be installed.

20. Practical troubleshooting recipes

“Why did nothing run?”

Run --dry-run. Check whether a supported build file exists, whether the directory is ignored, and whether the project actually defines the relevant script/configuration.

“Why is Lint WARN?”

The project may have no linter configuration, or the configured executable may be missing. This is intentionally not a code failure.

“Why are Tests SKIP?”

Look for a preceding Build or Lint failure, an omitted stage, no detected test command, or no_tests_found.

“Why is Coverage missing?”

Check that the coverage command ran, its report was written during this run, the report format is supported, and the output did not only contain an unrecognized percentage format.

“Why did the tool not run eslint/ruff?”

Being listed as a dependency is not enough. The project must declare it with a script or recognized configuration.

“Why does the report say WARN instead of FAIL?”

Missing tools and dependencies are setup problems. The tool reserves FAIL for command failures and the explicit no-tests coverage rule.

21. Study exercises

Exercise 1: A JavaScript project has lint:fix, test, and build scripts. Which scripts are eligible?

Answer

test and build. lint:fix is skipped because its name indicates a fixer.

Exercise 2: Build returns a dependency-resolution error. Does the build gate block later stages?

Answer

The result becomes a dependency warning when it matches the language's dependency patterns, so it is not treated as a code failure and does not activate the build gate.

Exercise 3: Lint fails, but Tests is explicitly requested. Does Tests run?

Answer

No. A Lint FAIL or TIMEOUT activates the lint gate and Tests/Coverage are skipped.

Exercise 4: A repository has an old coverage XML with 95%, but the new coverage command writes no file. What happens?

Answer

The old file is ignored as stale. The tool may parse a percentage from fresh output; otherwise Coverage is WARN coverage_missing.

Exercise 5: What is the difference between Supported and Tested?

Answer

Supported means a rulebook entry exists. Tested means the applicable fixture set has been verified with expected results and real tools.

Exercise 6: A team wants coverage below 80% to fail. Does v1 support this?

Answer

No. Coverage thresholds are intentionally out of scope and require a future specification decision.

22. Final mastery checklist

  • I can preview commands with --dry-run.
  • I understand that project scripts are trusted code, not harmless metadata.
  • I can explain the Build, Lint, Tests, and Coverage gates.
  • I can distinguish FAIL, WARN, SKIP, TIMEOUT, and INTR.
  • I know where the terminal result, JSON report, and full logs are found.
  • I know why installed tools are not automatically run.
  • I can explain fresh coverage and the no-tests rule.
  • I can name at least three handled edge cases.
  • I can name at least three known gaps.
  • I can describe the role of languages.toml.
  • I can add a language fixture without weakening the safety model.

23. One-page mental model

Trust the repository?        If no: do not run it. If unsure: dry-run first.
What is the input?           A folder, not a zip, URL, or single file.
What is discovered?          Supported build files become independent projects.
What gets executed?          Only project-defined, non-risky commands.
What is the order?           Build -> Lint -> Tests -> Coverage.
What blocks what?             Build failure blocks all; lint failure blocks later;
                              test failure blocks coverage.
What is honest evidence?      WARN is not PASS; SKIP is not PASS; no tests fail coverage.
What is produced?             Human table + masked bounded JSON + full logs.
What is not in v1?            Sandbox, installs, parallelism, thresholds, CI,
                              changed-files mode, and structured findings.
